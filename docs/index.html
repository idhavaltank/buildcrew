Get started

BuildCrew works best when it can read the repository it is helping with. Open the project in your AI coding tool (host), make sure its existing instructions are available, and have a specific task or question ready.

  1. Install BuildCrewChoose the supported plugin-package installation or a direct BuildCrew skill installation from the installation section below.
  2. Start a new sessionNew sessions load newly installed skills and prevent stale instructions from an earlier conversation.
  3. Begin with contextTell BuildCrew the goal, target area, constraints, and how success will be measured. Ask it to inspect before editing.
  4. Review the planConfirm the scope and approach before asking BuildCrew to implement anything.
  5. Verify the resultAsk for focused tests or checks, then review the evidence and remaining risk.

Your first prompt

Use BuildCrew to inspect this repository and plan a small feature. Do not edit files yet.

Good practice: Start with a small bug fix or feature. It makes the workflow easy to evaluate and keeps the first feedback concrete.

Installation

BuildCrew is an installable plugin package containing a portable skill. Choose the installation method that matches your AI coding tool. Installation is inert until the host loads BuildCrew and runs the one-time activation and onboarding flow.

Follow these steps in order: Install BuildCrew, configure global Codex-level activation, start a fresh session, and verify the setup.

Host runtime configuration for multi-agent execution

What does “host” mean? The host is the AI coding tool that loads and runs BuildCrew—for example, Codex, Claude Code, Cursor, Windsurf, Gemini CLI, or another supported tool.

Installing BuildCrew provides the workflow, agent roles, routing rules, and evidence contracts. It does not automatically create live sub-agents by itself. Real multi-agent execution requires the selected host to be configured with a runtime that can start agents and return their results.

Setup What happens
Skill installed only The host’s lead AI follows the BuildCrew workflow by itself.
Host runtime configured BuildCrew can select and spawn the required specialist agents automatically.
Host runtime unavailable BuildCrew continues with the lead AI and reports that separate agent execution is unavailable.

Live multi-agent execution requires an approved native-agent executor (the component that starts an agent), a model provider (the AI model service), a runtime coordinator (the component that manages agent assignments), a project scope, and execution permissions. Configure each AI coding tool separately; installing BuildCrew in one host does not configure it in another. BuildCrew never claims that agents ran unless the host returns valid execution evidence.

Review before installing: A skill is instruction and resource content supplied to an AI agent. Read the files and understand any scripts or hooks before enabling an external package.

Step 3: Start a fresh session and verify activation

Reload Codex or start a new session, open any repository, then send an ordinary request without naming BuildCrew:

Verify that the response follows the BuildCrew workflow and reports what it inspected. If the host cannot confirm persistent activation, use BuildCrew explicitly and follow the host-specific limitation it reports.

Core concepts

BuildCrew is an installable plugin package containing the BuildCrew skill, lifecycle workflow, and set of evidence-bound contracts—rules that connect decisions to verifiable evidence—working together.

Part Purpose Location
Plugin Distribution, metadata, presentation, and installation. plugin.json
Skill Instructions the agent follows during engineering work. SKILL.md
Documentation Human-facing setup, guides, examples, and reference. docs/index.html

Context and memory: BuildCrew performs a bounded local memory lookup for every input. The first project interaction uses one-time onboarding. Actionable work starts or resumes by exact task identity—the same task, project, and acceptance criteria—and closure stores only sanitized, scoped, evidence-backed learning. Current source remains more authoritative than memory.

01 · Understand

Context before code

Classify the input, run bounded memory lookup, then inspect the task, repository instructions, relevant source, tests, dependencies, and constraints.

02 · Reuse

Use what exists

Look for existing components, helpers, patterns, and conventions before adding new structure.

03 · Build

Smallest complete change

Make the smallest complete change that satisfies the request, reuses existing patterns, and preserves safeguards.

04 · Verify

Show the evidence

Run checks appropriate to the risk and report evidence, limitations, and residual risk.

BuildCrew operating modes

BuildCrew selects the appropriate mode based on the task’s complexity and risk. You can also request a specific mode when the task requires it.

Mode Use it for Editing
Lightweight Direct answers and narrow validation with bounded lookup. No
Normal Requirement gate, targeted analysis, implementation, review, and focused checks. Yes
Coupled Risk-tiered work with evidence waves, serialized boundaries, and strict receipts. When required
Shadow Compare route, risk, topology, and receipts without activation or mutation. No
FAST_DAILY Bounded routine mobile or Flutter source work without verified risk signals. Source-only

Trust rule: Never present a test as passing unless it actually ran, or imply that static inspection proves production behavior.

Workflows

Choose the BuildCrew route that matches the work. Routine changes stay lightweight; coupled or risky changes receive stronger planning, evidence, and review.

Understand and plan

Use BuildCrew to inspect the repository, retrieve relevant context, and produce a bounded implementation plan for adding an empty state to the profile screen. Do not edit files.

Implement

Use BuildCrew to implement the approved plan. Reuse existing patterns, keep the change focused, and run the relevant checks.

Review and verify

Use BuildCrew to review this diff for correctness, security, missing evidence, unnecessary complexity, and runtime limitations.

Complete and learn

At completed, blocked, or paused closure, record the evidence, residual risk, worklog, and sanitized learning outcome. Candidate knowledge requires separate review before canonical memory promotion.

Escalate when needed: Security boundaries, data migrations, release configuration, shared abstractions, mobile platform behavior, and production-only behavior deserve broader verification.

Multi-agent engineering team

When the host runtime supports agent execution, BuildCrew can coordinate specialist agents for larger or higher-risk work. For example, a project architecture request may use the following sequence:

  1. Understand the requestThe Orchestrator and Context Coordinator define the goal, scope, and acceptance criteria.
  2. Research the projectThe Knowledge Retriever and Codebase Analyst inspect documentation, source, dependencies, and existing patterns.
  3. Design the architectureThe Solution Architect turns the verified findings into a bounded architecture proposal.
  4. Review and validateThe Independent Reviewer checks risks and gaps, then the Final Validator confirms the evidence.

These agents are selected according to the task. If the host cannot spawn agents, the lead AI follows the same workflow and reports the capability limitation honestly.

Adapt these patterns to your repository and constraints.

Regression risk

Bug fix

Fix a retry loop that duplicates network requests. BuildCrew should trace the path, confirm the root cause, add a regression check, and report runtime risk.

New project

Do not invent architecture blindly. First ask about users, goals, core features, technology preferences, data, testing, security, and deployment expectations.

Undocumented project

Learn from source, configuration, dependencies, and tests. Record the documentation gap, save reusable context through the controlled learning path, and avoid treating assumptions as facts.

Completion response

  1. Summary: what was requested and what was done.
  2. Changed files: the files or areas that moved.
  3. Verification: commands, tests, inspections, or previews that actually ran.
  4. Not checked: relevant checks that did not run.
  5. Risk: assumptions, runtime limitations, or follow-up validation.

FAQ

Is BuildCrew a plugin or a skill?

BuildCrew is an installable plugin package that contains the BuildCrew skill. The plugin handles distribution and metadata; the skill contains the provider-neutral engineering workflow.

Does BuildCrew write code automatically?

Only when the host routes an actionable request and you authorize the work. The recommended workflow begins with onboarding or context lookup, current-source inspection, and a bounded plan.

Does BuildCrew guarantee correct code?

No. It improves understanding, implementation, memory continuity, and verification. It cannot prove production, browser, device, or provider behavior that was not exercised.

Does installation activate BuildCrew automatically?

Installation is inert. Persistent every-input use requires the host's supported global instruction, lifecycle hook, or equivalent loading mechanism. Global activation is configured once per installation and host; project onboarding prevents the introduction from repeating for each repository.

Does BuildCrew spawn agents automatically?

BuildCrew selects the required roles automatically only when the host runtime supports agent execution. Without that configuration, the lead AI follows the same workflow and reports that separate agent execution is unavailable.

What is a host?

A host is the AI coding tool that loads and runs BuildCrew, such as Codex, Claude Code, Cursor, Windsurf, or Gemini CLI. Each host must be configured separately for live multi-agent execution.

What happens when agent execution is unavailable?

BuildCrew continues with the lead AI. It can still inspect the project, plan changes, implement approved work, run available checks, and report evidence without pretending that separate agents ran.

How does BuildCrew handle memory?

Every input may perform a bounded local lookup. Actionable work can start or resume an exact task. At closure, BuildCrew stores only sanitized, scoped, evidence-backed learning; current source still outranks memory.
